# LAB-005 — Własny Lambda authorizer dla HTTP API

## Goal

Nauczyć się wdrażać **własny** mechanizm autoryzacji dla **HTTP API** w API Gateway, w którym decyzję `allow/deny` podejmuje osobna funkcja Lambda (authorizer), a logika biznesowa działa w oddzielnej funkcji backendowej.

## Why This Approach

`Project decision`

W tym labie wybieramy jeden spójny wariant: **HTTP API** + **Lambda authorizer typu REQUEST** + **payload format 2.0** + **simple responses**. Ten wariant jest prostszy do uruchomienia niż pełne polityki IAM zwracane z authorizera i dobrze pokazuje separację odpowiedzialności: authorizer decyduje o dostępie, backend realizuje biznes.

## Story / background

Firma ma publiczny endpoint z danymi klienta, ale reguły dostępu są niestandardowe: zależą od planu subskrypcji i identyfikatora tenant. Nie chcą mieszać tych reguł z kodem biznesowym endpointu. Potrzebują oddzielnego komponentu autoryzacji, który można rozwijać niezależnie.

## Czego się nauczysz

- Jak skonfigurować **Lambda authorizer** dla HTTP API (`authorizer_type = REQUEST`).
- Jak działa **payload 2.0** dla zdarzenia authorizera i co authorizer zwraca w trybie **simple response**.
- Jak połączyć chronioną trasę API z autoryzatorem (`authorization_type = CUSTOM`).
- Jak propagować kontekst autoryzacji do backendu i zweryfikować decyzję `allow/deny`.
- Jak testować scenariusze: brak tożsamości, token niepoprawny, token poprawny.

## Decyzje architektoniczne

### 1. Authorizer jako oddzielna Lambda

`Project decision` + `Best practice recommendation`

Reguły dostępu trzymamy osobno od logiki biznesowej. Dzięki temu backend nie zna szczegółów tokena, a zmiany reguł dostępu nie wymagają zmian w funkcji biznesowej.

### 2. REQUEST authorizer + payload 2.0 + simple response

`Project decision`

API Gateway wysyła do authorizera zdarzenie w formacie 2.0, a authorizer zwraca prostą odpowiedź:

```json
{ "isAuthorized": true/false, "context": { "...": "..." } }
```

To zmniejsza złożoność na początku nauki.

### 3. Identity source oparty o nagłówek Authorization

`Platform requirement` + `Project decision`

Wykorzystujemy `$request.header.Authorization`. Gdy klient nie wyśle tego nagłówka, API Gateway może odrzucić request bez wywoływania authorizera.

### 4. Cache authorizera domyślnie wyłączony

`Simplification for this lab`

W szkielecie ustawiamy `authorizer_result_ttl_in_seconds = 0`, żeby każda próba testowa wywoływała authorizer i dawała przewidywalny wynik podczas nauki.

## Architektoniczny szkic rozwiązania

```text
Klient (curl / SPA)
  │
  ├─ GET /public  ───────────────► HTTP API ───────────────► Lambda biznesowa
  │
  └─ GET /profile (Authorization) ► HTTP API
                                │
                                ├─ Lambda authorizer (REQUEST, payload 2.0)
                                │      └─ decyzja allow/deny + context
                                │
                                └─ (allow) Lambda biznesowa
```

## Jak poznam, że działa (walidacja)

- [ ] `terraform apply` kończy się sukcesem.
- [ ] `GET /public` zwraca `200`.
- [ ] `GET /profile` bez `Authorization` zwraca odmowę (typowo `401`).
- [ ] `GET /profile` z niepoprawnym tokenem zwraca odmowę (typowo `403` lub `401`, zależnie implementacji authorizera).
- [ ] `GET /profile` z poprawnym tokenem testowym zwraca `200`.
- [ ] W logach backendu nie ma pełnej wartości tokena.

## Pułapki

1. Brak uprawnienia `aws_lambda_permission` dla authorizera powoduje błędy 5xx po stronie API Gateway.
2. Niezgodność `handler` w Terraform z nazwą assembly/klasy powoduje błąd uruchomienia funkcji.
3. Zbyt ogólne logowanie nagłówków może ujawnić token w CloudWatch.
4. Włączenie cache authorizera bez przemyślenia klucza cache utrudnia testy i diagnozę.
