# LAB-009 — Container image dla Lambdy

## Goal

Nauczyć się wdrażać funkcję AWS Lambda jako obraz kontenera z Amazon ECR i wystawić ją przez HTTP API, zachowując spójny i przewidywalny przepływ build -> push -> deploy -> walidacja.

## Why This Approach

`Project decision`

W tym labie wybieramy jeden wariant: **Lambda package type `Image` + prywatne repozytorium ECR + HTTP API (`$default` stage, payload 2.0)**. Ten wariant pokazuje najważniejsze różnice względem ZIP deployment, ale pozostaje prosty operacyjnie dla początkującej osoby.

## Story / background

Zespół utrzymuje endpoint dla partnerów, ale chce większej kontroli nad środowiskiem uruchomieniowym (biblioteki systemowe i deterministyczny obraz). Dotychczasowe wdrożenia ZIP są szybkie, ale trudniej je ustandaryzować między CI i lokalnym buildem. Decyzja: przejście na model image-based dla jednej funkcji.

## Czego się nauczysz

- Czym różni się Lambda `package_type = "Image"` od wdrożenia ZIP.
- Jak działa relacja Lambda <-> ECR (repozytorium, tag obrazu, URI obrazu).
- Jak przygotować i wypchnąć obraz kontenera pod Lambdę (.NET 8).
- Jak podpiąć funkcję image-based do HTTP API (AWS_PROXY, payload 2.0).
- Jak walidować działanie endpointu i diagnozować typowe błędy image pull/startup.

## Założenia

- Ukończony co najmniej jeden wcześniejszy lab z HTTP API i Terraform.
- Region: `eu-central-1` (`Project decision`).
- Runtime w obrazie: .NET 8 na bazowym obrazie AWS dla Lambda (`Project decision`).
- Architektura funkcji: `x86_64` (`Project decision`).
- Terraform >= 1.6 oraz skonfigurowane poświadczenia AWS.

### Oznaczenia używane w tym labie

- `Platform requirement` — wymaganie lub twarde zachowanie AWS.
- `Project decision` — wybór przyjęty dla tego ćwiczenia.
- `Best practice recommendation` — zalecenie produkcyjne.
- `Simplification for this lab` — uproszczenie dydaktyczne.

## Decyzje architektoniczne

### 1) Lambda jako obraz kontenera

`Platform requirement` + `Project decision`

Lambda uruchamiana jako obraz (`package_type = "Image"`) musi wskazywać gotowy `image_uri` w ECR. W tym labie Terraform tworzy repozytorium ECR, a Ty samodzielnie publikujesz obraz i ustawiasz tag.

### 2) Jedna trasa `GET /health` na HTTP API

`Simplification for this lab`

Używamy jednej trasy diagnostycznej, aby skupić się na lifecycle obrazu (build/push/deploy), nie na logice routingu.

### 3) Stage `$default` z `auto_deploy = true`

`Project decision`

Dla prostego flow uczącego wybieramy domyślny stage, bez ręcznego wersjonowania deploymentów API.

### 4) Rozdział ownership zasobów

`Best practice recommendation`

- Terraform-managed: ECR repo, Lambda, IAM role, HTTP API, route, integration, permission.
- Platform-managed: runtime execution environment kontenera podczas invoke.

## Architektoniczny szkic rozwiązania

```text
Lokalny Docker build
  │
  ├─ docker push -> Amazon ECR (repo: lab009-lambda-image)
  │
  ▼
AWS Lambda (package type: Image, image_uri = <ecr_url>:<tag>)
  │
  ▼
HTTP API (route: GET /health, stage: $default)
  │
  ▼
Klient (curl)
```

## Krok po kroku

1. **Przygotuj kod funkcji**
   - Utwórz projekt np. `src/LAB-009/ImageLabFunction/`.
   - Dodaj prosty handler zwracający `200` i JSON z informacją o wersji obrazu.
   - `TODO(lab-009)`: dopasuj namespace/handler do własnego projektu.

2. **Zbuduj obraz kontenera lokalnie**
   - Przygotuj `Dockerfile` oparty o oficjalny obraz AWS Lambda dla .NET 8.
   - Zbuduj obraz:
   ```bash
   docker build \
     --platform linux/amd64 \
     --provenance=false \
     --sbom=false \
     --build-arg IMAGE_TAG=v1 \
     -t lab009-lambda:dev \
     src/LAB-009/ImageLabFunction
   ```
   `Simplification for this lab` + `Best practice recommendation`  
   Nowsze Docker/BuildKit potrafią domyślnie doklejać attestacje do manifestu obrazu; Lambda często kończy się wtedy błędem w stylu *“image manifest … media type … is not supported”*. Wyłączenie `--provenance/--sbom` (albo `BUILDX_NO_DEFAULT_ATTESTATIONS=1`) omija ten problem — patrz dokumentacja Dockera o attestacjach: https://docs.docker.com/build/attestations/

3. **Terraform init oraz utworzenie samego ECR**
   ```bash
   cd infra/terraform/labs/LAB-009
   terraform init
   terraform plan
   terraform apply -target=aws_ecr_repository.lambda
   ```
   Po tym kroku masz utworzone repozytorium ECR i możesz bezpiecznie wypchnąć pierwszy obraz.

4. **Zaloguj się do ECR i wypchnij obraz**
   ```bash
   AWS_ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
   AWS_REGION=eu-central-1
   ECR_REPO="${AWS_ACCOUNT_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com/lab009-lambda-image"

   aws ecr get-login-password --region "${AWS_REGION}" \
     | docker login --username AWS --password-stdin "${AWS_ACCOUNT_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com"

   docker tag lab009-lambda:dev "${ECR_REPO}:v1"
   docker push "${ECR_REPO}:v1"
   ```

   Jeśli wcześniej wypchnąłeś obraz bez flag z kroku 2 i Lambda zwraca błąd o *unsupported media type*, usuń tag `v1` w ECR (albo użyj nowego tagu, np. `v1-fix`) i powtórz build+push z kroku 2.

5. **Ustaw tag obrazu i wdroż pełen stos**
   - W `terraform.tfvars` ustaw:
   ```hcl
   image_tag = "v1"
   ```
   - Uruchom pełny apply:
   ```bash
   terraform apply
   ```

6. **Zweryfikuj endpoint**
   ```bash
   curl -i "$(terraform output -raw health_url)"
   ```
   Oczekiwane: `HTTP/1.1 200` i JSON z odpowiedzią funkcji.

## Jak poznam, że działa (walidacja)

- [ ] `terraform apply -target=aws_ecr_repository.lambda` przechodzi bez błędów.
- [ ] Pełny `terraform apply` przechodzi bez błędów po wypchnięciu obrazu.
- [ ] Obraz z tagiem ustawionym w `image_tag` istnieje w ECR.
- [ ] `GET /health` zwraca `200`.
- [ ] Logi funkcji pojawiają się w CloudWatch (`/aws/lambda/lab009-image-function`).
- [ ] Zmiana tagu obrazu (np. `v1` -> `v2`) i ponowny `terraform apply` aktualizuje zachowanie endpointu.

## Pułapki

1. Tag obrazu ustawiony w Terraform nie istnieje w ECR -> Lambda nie uruchamia nowej wersji poprawnie.
2. Obraz zbudowany dla innej architektury niż Lambda (`x86_64`) może kończyć się błędem startu.
3. Brak uprawnień IAM do logowania powoduje brak diagnostyki w CloudWatch.
4. Przekonanie, że `terraform apply` sam zbuduje i wypchnie obraz — ten lab celowo rozdziela IaC od procesu build/push.
5. Docker BuildKit domyślnie potrafi doklejać attestacje do manifestu obrazu; Lambda może zwrócić `InvalidParameterValueException` o nieobsługiwanym `media type` — wtedy przebuduj obraz z `--provenance=false --sbom=false` (albo `BUILDX_NO_DEFAULT_ATTESTATIONS=1`) i wypchnij ponownie.
