# LAB-001 — Publiczny endpoint statusowy w AWS Lambda (.NET 8) z HTTP API Gateway

## Story / background

Zespół operacyjny chce wystawić bardzo prosty publiczny endpoint `GET /health` dla wewnętrznego mikroserwisu raportowego. Nie chcą utrzymywać EC2, nie potrzebują Load Balancera i nie chcą wchodzić jeszcze w kontenery. Potrzebują jednego publicznego URL, który zwróci `200 OK` oraz mały JSON ze statusem usługi.

W tym labie budujesz funkcję **AWS Lambda w .NET 8 na managed runtime `dotnet8`**, pakujesz ją jako **zip deployment package** i wystawiasz przez **API Gateway HTTP API**. To jest świadomy wybór dydaktyczny: AWS oferuje też Function URL jako najprostszy sposób wystawienia funkcji po HTTP, ale tutaj celem jest nauczenie się podstawowego przepływu z API Gateway: **route → integration → stage → permission**.

---

## Czego się nauczysz

- Jak działa Lambda w modelu **managed runtime `dotnet8`**
- Jak wygląda **class library handler** w C# i jak Lambda go odnajduje
- Jak spakować funkcję do **zip deployment package**
- Jak skonfigurować **HTTP API Gateway** jako front door do Lambdy
- Jak działa **Lambda proxy integration**
- Jak zdefiniować minimalną infrastrukturę w Terraform
- Jak uniknąć konfliktu z `aws_cloudwatch_log_group`, gdy log group już istnieje

---

## Decyzje projektowe w tym labie

### 1. Używamy **HTTP API**, nie REST API

HTTP API jest lżejsze i tańsze od klasycznego REST API Gateway. Dla prostego endpointu zdrowia to jest właściwy wybór.

### 2. Używamy **payload format version 2.0**

Dla HTTP API to jest naturalny i uproszczony format eventu. W tym labie robimy to świadomie, zamiast mieszać HTTP API z typami payloadu 1.0.

### 3. Jawnie pinujemy architekturę do **`x86_64`**

Lambda wspiera zarówno `x86_64`, jak i `arm64`. W labie startowym wybieramy **`x86_64`**, żeby nie mnożyć zmiennych. To nie jest jedyna poprawna architektura — to po prostu jawna decyzja projektowa dla tego ćwiczenia.

### 4. Log group jest zarządzana przez Terraform

Domyślnie Lambda tworzy log group `/aws/lambda/<function-name>` automatycznie przy **pierwszym wywołaniu** funkcji. To bardzo często prowadzi do konfliktu: później Terraform próbuje utworzyć zasób, który już istnieje. Dlatego w tym labie tworzymy log group jawnie w Terraform i dodajemy procedurę importu, jeśli grupa już istnieje.

## Jak to działa pod maską

Przepływ żądania wygląda tak:

```text
Klient HTTP
    │
    ▼
[API Gateway — HTTP API]
    │  route: GET /health
    │  integration: Lambda proxy
    │  payload format: 2.0
    ▼
[Lambda — .NET 8 managed runtime]
    │  handler: HealthFunction::HealthFunction.Function::FunctionHandler
    │  package: function.zip
    ▼
[CloudWatch Logs]
```

Dla integracji proxy API Gateway przekazuje request do Lambdy jako event, a Lambda zwraca odpowiedź w formacie oczekiwanym przez proxy integration. Jeśli zwrócony format będzie niepoprawny, API Gateway może oddać `502`. Dla HTTP API przy stage `$default` endpoint jest serwowany spod bazowego URL API, bez dodatkowego segmentu stage.

## Krok 4 — podmień kod handlera

Plik: `src/LAB-001/HealthFunction/Function.cs`

```csharp
using Amazon.Lambda.APIGatewayEvents;
using Amazon.Lambda.Core;

[assembly: LambdaSerializer(typeof(Amazon.Lambda.Serialization.SystemTextJson.DefaultLambdaJsonSerializer))]

namespace HealthFunction;

public class Function
{
    public APIGatewayHttpApiV2ProxyResponse FunctionHandler(
        APIGatewayHttpApiV2ProxyRequest request,
        ILambdaContext context)
    {
        var method = request?.RequestContext?.Http?.Method ?? "UNKNOWN";
        var path = request?.RawPath ?? "/";

        context.Logger.LogInformation($"Request received: {method} {path}");

        var payload = new
        {
            status = "ok",
            service = "health-reporter",
            timestamp = DateTimeOffset.UtcNow.ToString("O")
        };

        return new APIGatewayHttpApiV2ProxyResponse
        {
            StatusCode = 200,
            Headers = new Dictionary<string, string>
            {
                ["Content-Type"] = "application/json"
            },
            Body = System.Text.Json.JsonSerializer.Serialize(payload)
        };
    }
}
```

### Dlaczego tak

- używamy typu eventu dla **HTTP API payload 2.0**
- logujemy metodę i ścieżkę, żeby łatwo potwierdzić wykonanie w CloudWatch
- używamy `DateTimeOffset.UtcNow`, bo to lepszy typ do pracy z czasem niż goły `DateTime`
- nie inicjalizujemy tu jeszcze klientów AWS SDK, bo funkcja nie używa żadnych zależności zewnętrznych

## Krok 6 — przygotuj Terraform

Plik: `infra/terraform/labs/LAB-001/main.tf`

```hcl
terraform {
  required_version = ">= 1.6.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "eu-central-1"
}

locals {
  function_name   = "health-function-lab001"
  lambda_zip_path = "${path.module}/../../../../artifacts/LAB-001/function.zip"
}

resource "aws_iam_role" "lambda_exec" {
  name = "health-function-lab001-exec-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Principal = {
          Service = "lambda.amazonaws.com"
        }
        Action = "sts:AssumeRole"
      }
    ]
  })
}

resource "aws_iam_role_policy_attachment" "lambda_basic_execution" {
  role       = aws_iam_role.lambda_exec.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole"
}

resource "aws_cloudwatch_log_group" "health" {
  name              = "/aws/lambda/${local.function_name}"
  retention_in_days = 14
}

resource "aws_lambda_function" "health" {
  function_name = local.function_name
  role          = aws_iam_role.lambda_exec.arn

  filename         = local.lambda_zip_path
  source_code_hash = filebase64sha256(local.lambda_zip_path)

  handler = "HealthFunction::HealthFunction.Function::FunctionHandler"
  runtime = "dotnet8"

  architectures = ["x86_64"]
  timeout       = 5
  memory_size   = 256

  depends_on = [
    aws_iam_role_policy_attachment.lambda_basic_execution,
    aws_cloudwatch_log_group.health
  ]
}

resource "aws_apigatewayv2_api" "health" {
  name          = "health-api-lab001"
  protocol_type = "HTTP"
}

resource "aws_apigatewayv2_integration" "health_lambda" {
  api_id = aws_apigatewayv2_api.health.id

  integration_type       = "AWS_PROXY"
  integration_uri        = aws_lambda_function.health.invoke_arn
  payload_format_version = "2.0"
}

resource "aws_apigatewayv2_route" "health" {
  api_id    = aws_apigatewayv2_api.health.id
  route_key = "GET /health"
  target    = "integrations/${aws_apigatewayv2_integration.health_lambda.id}"
}

resource "aws_apigatewayv2_stage" "default" {
  api_id      = aws_apigatewayv2_api.health.id
  name        = "$default"
  auto_deploy = true
}

resource "aws_lambda_permission" "allow_api_gateway" {
  statement_id  = "AllowHttpApiInvoke"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.health.function_name
  principal     = "apigateway.amazonaws.com"
  source_arn    = "${aws_apigatewayv2_api.health.execution_arn}/*/*"
}

output "api_base_url" {
  value = aws_apigatewayv2_api.health.api_endpoint
}

output "health_url" {
  value = "${aws_apigatewayv2_api.health.api_endpoint}/health"
}
```

## Krok 7 — uwaga o log group przed pierwszym `apply`

Jeżeli funkcja o tej nazwie była już kiedyś wywoływana, to log group `/aws/lambda/health-function-lab001` może już istnieć, bo Lambda tworzy ją automatycznie przy pierwszym invoke. Wtedy `terraform apply` może zakończyć się błędem `already exists`. W takim przypadku **nie usuwaj odruchowo zasobu z Terraform**. Zamiast tego zaimportuj istniejącą log group do state.

```bash
cd infra/terraform/labs/LAB-001
terraform import aws_cloudwatch_log_group.health /aws/lambda/health-function-lab001
```

Dopiero potem uruchom plan i apply.

## Pułapki i antywzorce

### 1. Mieszanie HTTP API z payloadem 1.0 bez jawnej decyzji

To jest jeden z najczęstszych błędów. HTTP API wspiera `1.0` i `2.0`, ale w IaC trzeba to określić jawnie. W tym labie używamy wyłącznie `2.0`. Nie mieszaj tego z typami eventu dla REST API lub payloadu 1.0.

### 2. Niejawna architektura funkcji

Nie pisz w dokumentacji, że Lambda „wymaga `linux-x64`”. To jest nieprecyzyjne. Lambda wspiera `x86_64` i `arm64`; w tym labie po prostu wybierasz `x86_64`. ZIP musi być zgodny z architekturą funkcji.

### 3. Pozwalanie Lambdzie utworzyć log group, a potem próba tworzenia jej przez Terraform

To klasyczny konflikt ownership. Albo log group należy do Terraform od początku, albo pozwalasz tworzyć ją AWS. W tym labie wybieramy wariant pierwszy. Jeżeli grupa już istnieje — importujesz ją.

### 4. Brak `source_code_hash`

Bez tego Terraform może nie zaktualizować kodu funkcji po zmianie ZIP-a. To częsty powód sytuacji „apply przeszedł, ale działa stary kod”.

### 5. Niepoprawny handler

W managed runtime .NET handler musi mieć format:

`AssemblyName::Namespace.ClassName::MethodName`

Dla tego projektu jest to:

`HealthFunction::HealthFunction.Function::FunctionHandler`

### 6. Nieporozumienie wokół URL API

Przy stage `$default` URL wygląda tak:

`https://{api-id}.execute-api.{region}.amazonaws.com/health`

Jeśli użyjesz nazwanego stage, adres będzie inny. W tym labie używamy tylko `$default`.
