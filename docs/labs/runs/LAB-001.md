# LAB-001 — Publiczny endpoint dla zespołu statusowego

## Story / background

Zespół operacyjny chce wystawić bardzo prosty endpoint `/health` dla wewnętrznego mikroserwisu raportowego. Nie mają serwera, nie chcą utrzymywać EC2, nie potrzebują Load Balancera. Potrzebują tylko jednego publicznego URL, który odpowie `200 OK` z podstawowym JSON-em statusowym.

Twoim zadaniem jest wdrożenie funkcji Lambda w .NET 8 (managed runtime) za pomocą HTTP API Gateway, z pełnym `zip deployment` i minimalnym Terraform.

---

## Czego się nauczysz

- Jak działa managed runtime dla .NET 8 w Lambda (bez kontenera, bez custom bootstrap)
- Jak zbudować i spakować deployment package (`.zip`) dla Lambdy w C#
- Jak wygląda podstawowy handler C# i jak Lambda go wywołuje
- Jak skonfigurować HTTP API w API Gateway jako "front door" do funkcji
- Jak wygląda przepływ requestu: `klient → API Gateway → Lambda → response`
- Jak napisać minimalny Terraform dla tego stosu

---

## Założenia

- Masz konto AWS z odpowiednimi uprawnieniami (Lambda, API Gateway, IAM, CloudWatch Logs)
- Masz zainstalowane lokalnie: `dotnet` (SDK 8.x), `terraform >= 1.6`, `aws cli v2`
- Masz skonfigurowane credentials AWS (np. `aws configure` lub zmienne środowiskowe)
- Rozumiesz podstawy C# i pojęcie funkcji jako jednostki wdrożenia
- Nie zakładamy żadnej wcześniejszej wiedzy o Lambdzie — to jest punkt startowy

---

## Architektoniczny szkic rozwiązania

```
Klient HTTP
    │
    ▼
[API Gateway — HTTP API]
    │  route: GET /health
    │  integration: Lambda proxy
    ▼
[Lambda — .NET 8 managed runtime]
    │  handler: HealthFunction::HealthFunction.Function::FunctionHandler
    │  package: function.zip (zip deployment)
    ▼
CloudWatch Logs (automatyczne logi)
```

**Kluczowe relacje:**
- API Gateway HTTP API używa **proxy integration** — cały request (headers, query string, body) jest przekazywany jako JSON event do Lambdy
- Lambda zwraca JSON zgodny ze schematem `APIGatewayProxyResponse` (status code, headers, body)
- Managed runtime `dotnet8` oznacza, że AWS zarządza środowiskiem wykonania — Ty dostarczasz tylko skompilowany kod

## Krok po kroku

### 1. Utwórz projekt Lambda w .NET 8

```bash
# Zainstaluj templaty Lambda dla dotnet (jeśli jeszcze nie masz)
dotnet new install Amazon.Lambda.Templates

# Utwórz nowy projekt w katalogu src/
mkdir -p src/HealthFunction
cd src/HealthFunction
dotnet new lambda.EmptyFunction --name HealthFunction --framework net8.0
```

> **Co się dzieje:** Template tworzy minimalny projekt z handlerem `FunctionHandler` i przykładowym typem wejścia/wyjścia.

### 2. Dostosuj handler do odpowiedzi HTTP

Otwórz `src/HealthFunction/src/HealthFunction/Function.cs` i zastąp zawartość handlera:

```csharp
using Amazon.Lambda.Core;
using Amazon.Lambda.APIGatewayEvents;

[assembly: LambdaSerializer(typeof(Amazon.Lambda.Serialization.SystemTextJson.DefaultLambdaJsonSerializer))]

namespace HealthFunction;

public class Function
{
    public APIGatewayProxyResponse FunctionHandler(
        APIGatewayProxyRequest request,
        ILambdaContext context)
    {
        context.Logger.LogInformation($"Request received: {request.HttpMethod} {request.Path}");

        return new APIGatewayProxyResponse
        {
            StatusCode = 200,
            Headers = new Dictionary<string, string>
            {
                { "Content-Type", "application/json" }
            },
            Body = System.Text.Json.JsonSerializer.Serialize(new
            {
                status = "ok",
                service = "health-reporter",
                timestamp = DateTime.UtcNow.ToString("o")
            })
        };
    }
}
```

Dodaj potrzebne pakiety NuGet:
```bash
cd src/HealthFunction/src/HealthFunction
dotnet add package Amazon.Lambda.APIGatewayEvents
```

> **Uwaga:** `APIGatewayProxyRequest` i `APIGatewayProxyResponse` to typy ze schematem Payload Format Version 1.0. HTTP API może też używać formatu 2.0 — w tym labie używamy 1.0 dla maksymalnej klarowności.

### 3. Zbuduj i spakuj funkcję

```bash
cd src/HealthFunction/src/HealthFunction

# Opublikuj jako self-contained deployment dla linux-x64
dotnet publish -c Release -r linux-x64 --no-self-contained -o ./publish

# Spakuj do ZIP
cd publish
zip -r ../../../../function.zip .
cd ../../../../
```

> **Ważne:** Lambda managed runtime `dotnet8` wymaga, żeby w ZIP-ie był skompilowany kod dla `linux-x64`. Flaga `--no-self-contained` oznacza, że runtime jest dostarczony przez AWS.

### 4. Przygotuj infrastrukturę Terraform

Przejdź do `infra/terraform/labs/LAB-001/` i uzupełnij pliki IaC zgodnie ze szkieletem (patrz sekcja Terraform poniżej).

```bash
cd infra/terraform/labs/LAB-001/
terraform init
terraform plan
terraform apply
```

> **Zanim uruchomisz apply:** przejrzyj plan. Sprawdź, że Lambda ma poprawny handler string i wskazuje na istniejący plik ZIP.

### 5. Przetestuj endpoint

Po `terraform apply` skopiuj output `api_url` i wywołaj endpoint:

```bash
curl -i https://<api-id>.execute-api.eu-central-1.amazonaws.com/health
```

Spodziewany wynik:
```json
{"status":"ok","service":"health-reporter","timestamp":"2026-04-14T10:00:00.000Z"}
```

## Terraform / IaC

### Co musisz zrozumieć przed pisaniem kodu

- `aws_lambda_function` wymaga `filename` (ścieżka do ZIP) lub `s3_bucket`/`s3_key`
- `source_code_hash` w Terraform pozwala wykrywać zmiany w paczce ZIP
- IAM role dla Lambdy musi mieć **trust policy** pozwalającą `lambda.amazonaws.com` na `AssumeRole`
- Minimalne uprawnienia do logowania: policy `AWSLambdaBasicExecutionRole`
- HTTP API w API Gateway to `aws_apigatewayv2_api` z `protocol_type = "HTTP"`
- Integracja Lambda proxy: `aws_apigatewayv2_integration` z `integration_type = "AWS_PROXY"`
- Trasa: `aws_apigatewayv2_route` z `route_key = "GET /health"`
- Stage z auto-deploy: `aws_apigatewayv2_stage` z `auto_deploy = true`
- Lambda permission: `aws_lambda_permission` żeby API Gateway mogło wywołać funkcję

### Szkielet do uzupełnienia (`main.tf`)

Pliki są w `infra/terraform/labs/LAB-001/`. Szkielet zawiera:
- Provider i wersje — **już gotowe**
- Zasoby Lambda, IAM role, HTTP API — **do uzupełnienia przez Ciebie**

## Pułapki i typowe błędy

### 1. Niepoprawny handler string
Handler w Terraform musi być w formacie `AssemblyName::Namespace.ClassName::MethodName`.  
Przykład: `HealthFunction::HealthFunction.Function::FunctionHandler`  
Błąd objawi się jako `Runtime.HandlerNotFound` w logach — nie jako błąd Terraform.

### 2. ZIP spakowany z katalogiem zamiast zawartości
Jeśli spakujesz `publish/` jako katalog (nie zawartość), Lambda nie znajdzie pliku DLL.  
Zawsze wchódź do katalogu `publish/` i stamtąd robisz `zip -r ../function.zip .`

### 3. Brak `aws_lambda_permission` dla API Gateway
Lambda nie wywoła się, jeśli API Gateway nie ma uprawnień. Błąd: HTTP 500 lub `{"message":"Internal Server Error"}` bez żadnego logu w Lambda.  
Sprawdź, czy dodałeś `aws_lambda_permission` z `principal = "apigateway.amazonaws.com"`.

### 4. Stary ZIP w Terraform (brak `source_code_hash`)
Terraform nie wie, że ZIP się zmienił, jeśli nie podasz `source_code_hash = filebase64sha256(...)`.  
Bez tego `terraform apply` nie zaktualizuje kodu funkcji nawet po przebudowaniu paczki.

## Cleanup i cost hygiene

Lambda i HTTP API Gateway są w darmowym tierze dla małego ruchu, ale **zawsze sprzątaj po labie**:

```bash
cd infra/terraform/labs/LAB-001/
terraform destroy
```

Sprawdź manualnie w konsoli AWS:
- [ ] Lambda function usunięta
- [ ] API Gateway (HTTP API) usunięty
- [ ] IAM role usunięta
- [ ] CloudWatch Log Group usunięty (Terraform domyślnie tego nie robi — usuń ręcznie lub dodaj `aws_cloudwatch_log_group` z `force_destroy = true`)

**Orientacyjny koszt laba:** praktycznie $0 przy ruchu testowym (Lambda free tier: 1M wywołań/mies., API Gateway HTTP API: 1M wywołań/mies.).
