# LAB-010 — Custom runtime (ZIP + `provided.al2023`)

## Story / background

Zespół platformowy chce zrozumieć mechanikę Lambdy „pod maską”: jak środowisko uruchamia Twój kod, skąd bierze zdarzenie i jak zwraca odpowiedź, zamiast polegać wyłącznie na managed runtime. Ten lab realizuje to przez **własny runtime oparty na pliku `bootstrap`** i **Lambda Runtime API**, z publicznym wywołaniem przez HTTP API (jak w innych labach repozytorium), żebyś mógł zweryfikować zachowanie końcowe `curl`-em.

## Czego się nauczysz

- Jak działa **Lambda Runtime API** (`/runtime/invocation/next`, odpowiedzi i błędy wywołania).
- Dlaczego w OS-only runtime wejściem jest **`bootstrap`** i jak wiąże się to z **`_HANDLER`**.
- Jak **spakować** minimalny custom runtime jako ZIP i podpiąć go pod Lambdę z runtime **`provided.al2023`**.
- Kiedy custom runtime **ma sens**, a kiedy jest **kosztem złożoności** względem managed runtime lub obrazu kontenera.

## Założenia

- **Konto AWS** z uprawnieniami do Lambda, IAM, API Gateway HTTP API, CloudWatch Logs oraz (opcjonalnie) kosztowego budżetu na sandbox.
- **Terraform** `>= 1.6.0`, skonfigurowany provider AWS (np. profil SSO lub klucze — poza zakresem laba).
- **Środowisko budowania ZIP** zgodne z Unix (Linux, macOS, WSL). Na czystym Windowsie końcowe `chmod` i line endingi plików potrafią być problematyczne — **wymaganie platformy** dla tego laba: przygotuj archiwum w środowisku Unixowym.
- **Jeden region** na cały lab — domyślnie `eu-central-1` (decyzja projektowa spójna z innymi labami w repozytorium); możesz zmienić przez `var.aws_region`, ale wtedy **wszystkie** komendy i zasoby muszą być w tym samym regionie.
- Plik wdrożeniowy **`artifacts/LAB-010/function.zip` istnieje przed `terraform plan`**, bo Terraform liczy `source_code_hash` z pliku ZIP (tak samo jak w LAB-002).

## Decyzje architektoniczne (jeden wariant techniczny)

| Obszar | Decyzja dla LAB-010 | Uwaga |
|--------|---------------------|--------|
| Model wdrożenia | **ZIP** (nie container image) | Izoluje temat „runtime API + bootstrap” od warstwy obrazu Dockera. |
| OS-only runtime | **`provided.al2023`** | Oficjalna rodzina „provided” na Amazon Linux 2023; spójna z dokumentacją AWS dla custom runtime. |
| Konwencja handlera | **`function.handler`** | Zgodna z oficjalnym tutorial AWS: `function.sh` + symboliczny „handler” w stylu `plik.metoda`, który runtime odczytuje z **`_HANDLER`**. |
| Edge | **HTTP API (v2)** + `AWS_PROXY` + **payload 2.0** | Spójne z LAB-002 / LAB-009; jedna trasa `GET /health`. |
| Architektura CPU | **`x86_64`** | Domyślne ujednolicenie z innymi labami ZIP/.NET w repo. |

**Uproszczenie dydaktyczne:** nie budujemy produkcyjnego, wielojęzycznego runtime ani współbieżnego modelu jak w Lambda Managed Instances — tylko **pętlę obsługi zdarzeń** w jednym środowisku wykonawczym zgodnie z dokumentacją „classic” Lambda.

**Best practice (AWS):** traktuj custom runtime jako zaawansowany scenariusz; jeśli celem jest tylko inny język lub binarka, rozważ najpierw managed runtime, **provided** z gotowym bootstrapem od AWS lub obraz kontenera.

## Architektoniczny szkic rozwiązania

```text
Klient (curl)
    → HTTP API ($default) GET /health
        → integracja AWS_PROXY (payload 2.0)
            → Lambda (ZIP, runtime provided.al2023)
                → proces `bootstrap` (Twój kod)
                    ↔ Lambda Runtime API (HTTP, host z AWS_LAMBDA_RUNTIME_API)
                → (opcjonalnie) wywołanie logiki w `function.sh` wg `_HANDLER`
```

**Ownership zasobów:** wszystkie zasoby w tym labie są **Terraform-managed** (wyjątek: lokalny plik `artifacts/LAB-010/function.zip`, który budujesz sam i który nie jest „zasobem chmurowym”).

## Jak poznam, że działa (walidacja)

- `terraform output health_url` zwraca URL, a `curl -sS -o /dev/null -w "%{http_code}" <health_url>` daje **`200`** (przy poprawnej odpowiedzi z funkcji przez proxy HTTP API).
- W logach CloudWatch widać **report** z `Init Duration` przy pierwszym wywołaniu (nowa instancja) oraz `Duration` przy kolejnych — to potwierdza model „init raz na instancję” opisany w dokumentacji runtime.
- Przy celowym błędzie w `bootstrap` lub `function.sh` dostajesz czytelny błąd w logach (np. problem z Runtime API) zamiast „ciszy” — rozumiesz, **gdzie** rozdziela się warstwa runtime vs integracja API Gateway.

## Pułapki

- **`Runtime.InvalidEntrypoint`** — brak `bootstrap`, zła nazwa, brak bitu wykonywalności, lub **CRLF** zamiast LF w shebang.
- **`filebase64sha256` w Terraform** — jeśli ZIP nie istnieje pod ścieżką z `main.tf`, plan się wywali; najpierw zbuduj artefakt.
- **Zły `handler`** — musi być spójny z tym, co Twój `bootstrap` / runtime czyta z **`_HANDLER`** (patrz dokumentacja zmiennych środowiskowych runtime).
- **Mylenie „custom runtime” z „własnym obrazem”** — to osobne ścieżki; ten lab jest celowo na **ZIP + provided.al2023**.
- **Payload HTTP API 2.0** — funkcja dostaje inny kształt zdarzenia niż surowe `curl` z przeglądarki; do diagnozy używaj logów i dokumentacji Lambda + HTTP API.
