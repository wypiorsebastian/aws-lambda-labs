# LAB-006 — Observability dla publicznego API

## Goal

Nauczyć się budować podstawową obserwowalność dla HTTP API opartego o Lambda: logi dostępowe API Gateway, structured logging i metryki w funkcji, oraz ślady X-Ray do diagnozy opóźnień i błędów.

## Why This Approach

`Project decision`

W tym labie używamy jednego wariantu: **HTTP API** + **jedna Lambda backendowa** + **CloudWatch access logs na stage** + **Active X-Ray na funkcji** + **Powertools for AWS Lambda (.NET)** do structured logging i custom metrics. To daje prostą, spójną ścieżkę diagnostyczną bez mieszania wielu wzorców telemetrycznych.

## Story / background

Zespół widzi sporadyczne 5xx i rosnące opóźnienia endpointu publicznego, ale nie ma wspólnego miejsca, które łączy request API, logi funkcji i trace wykonania. Incydenty rozwiązywane są ręcznie, bez szybkiego wskazania: czy problem jest w API Gateway, Lambdzie, czy downstream.

## Czego się nauczysz

- Jak włączyć i czytać **access logs** dla HTTP API (`$default` stage).
- Jak skonfigurować Lambdę pod **X-Ray Active tracing**.
- Jak użyć **Powertools for AWS Lambda (.NET)** do structured logging i metryk EMF.
- Jak odróżnić problemy cold start / init od błędów ścieżki invoke.
- Jak walidować diagnostykę prostymi scenariuszami `200` i `5xx`.

## Decyzje architektoniczne

### 1. Jedna funkcja + kilka tras HTTP API

`Project decision` + `Simplification for this lab`

Skupiamy się na obserwowalności, nie na złożonym routingu. Jedna funkcja obsługuje trasy testowe:
- `GET /health` (szybki sukces),
- `GET /orders/{id}` (zwykły path biznesowy),
- `GET /fail` (kontrolowany błąd 5xx).

### 2. Access logs po stronie API Gateway na `$default` stage

`Platform requirement` + `Best practice recommendation`

API Gateway zapisuje zdarzenia request/response do dedykowanej grupy logów CloudWatch. Format logu jest JSON i zawiera klucze diagnostyczne (`requestId`, `routeKey`, `status`, `integrationLatency`, `integrationErrorMessage`).

### 3. Active tracing dla Lambda

`Platform requirement`

Funkcja działa z `tracing_config.mode = "Active"` oraz rolą wykonawczą z polityką `AWSXRayDaemonWriteAccess`.

### 4. Powertools (.NET) do logów i metryk

`Project decision` + `Best practice recommendation`

W kodzie funkcji użyj loggera i metryk Powertools. Telemetria z API Gateway + Lambda + X-Ray ma dać spójny obraz jednej ścieżki requestu.

## Architektoniczny szkic rozwiązania

```text
Klient (curl)
  │
  ▼
HTTP API ($default stage)
  ├─ access logs → CloudWatch Log Group (/aws/apigateway/lab006-http-access)
  └─ AWS_PROXY integration (payload 2.0)
       │
       ▼
Lambda .NET 8 (tracing: Active, Powertools logger/metrics)
  ├─ function logs → CloudWatch Log Group (/aws/lambda/public-observability-lab006)
  └─ traces → AWS X-Ray
```

## Jak poznam, że działa (walidacja)

- [ ] `terraform apply` przechodzi bez błędów.
- [ ] `GET /health` zwraca `200`.
- [ ] `GET /orders/{id}` zwraca `200` i dane testowe.
- [ ] `GET /fail` zwraca kontrolowany błąd (`5xx`).
- [ ] Access logs API Gateway zawierają `requestId`, `routeKey`, `status`, `integrationLatency`.
- [ ] Logi Lambda są structured i nie zawierają danych wrażliwych.
- [ ] X-Ray pokazuje ślady dla żądań i umożliwia odróżnienie init/invoke.

## Pułapki

1. Brak polityki `AWSXRayDaemonWriteAccess` w roli Lambdy uniemożliwia poprawne wysyłanie trace.
2. Brak `access_log_settings` na stage daje „ślepą plamę” po stronie API Gateway.
3. Logowanie pełnych payloadów lub nagłówków może ujawnić dane wrażliwe.
4. Mylne wnioski z pojedynczego requestu: X-Ray jest próbkowany (`sampling`) i nie każdy request musi mieć trace.
