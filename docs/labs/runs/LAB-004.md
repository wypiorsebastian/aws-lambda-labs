# LAB-004 — JWT dla publicznego HTTP API (Cognito + wbudowany JWT authorizer)

## Goal

Nauczyć się chronić **publiczne** HTTP API tak, aby wybrane trasy wymagały **poprawnego JWT** wydanego przez zaufany **OIDC issuer** (tu: **Amazon Cognito User Pool**), zrozumieć **propagację claims** do Lambdy (payload proxy **2.0**), skonfigurować **CORS** na poziomie API oraz świadomie odróżnić to od **Lambda authorizer** (następny lab).

## Why This Approach

`Project decision`

W jednym labie nie mieszamy wielu issuerów (Auth0, Okta, własny STS, wiele audience). **Jeden spójny wariant**: **HTTP API** + **JWT authorizer** wbudowany w API Gateway + **Cognito** jako źródło tokenów. Dzięki temu cały przepływ JWKS/issuer/audience jest **opisany w dokumentacji AWS** i da się go odtworzyć w Terraform bez zewnętrznych kont SaaS.

`Simplification for this lab`

**Domena niestandardowa (custom domain)** jest opisana **koncepcyjnie** i linkami — **nie** wdrażamy pełnego `AWS::ApiGatewayV2::DomainName` w tym szkielecie, żeby nie rozpychać laba o certyfikaty ACM i DNS.

## Story / background

Zespół wystawia publiczne API dla aplikacji mobilnej i SPA. Chcą, żeby **GET /public** był dostępny anonimowo (np. health/marketing), a **GET /claims** zwracał **bezpieczny podgląd** wybranych claims z tokena — bez implementowania walidacji JWT w kodzie Lambdy (robi to **API Gateway** przed invoke).

## Czego się nauczysz

- Jak skonfigurować **JWT authorizer** dla **HTTP API** (issuer, audience, identity source).
- Jak powiązać trasę z **JWT** vs trasę **bez** autoryzacji.
- Jak czytać **claims** w .NET z `APIGatewayHttpApiV2ProxyRequest` (`RequestContext.Authorizer.Jwt.Claims`).
- Jak ustawić **CORS** dla HTTP API i testować preflight (`OPTIONS`).
- Jak uzyskać token testowy z **Cognito** (`USER_PASSWORD_AUTH`) i wywołać API przez `curl`.

## Decyzje architektoniczne

### 1. Issuerem jest Cognito User Pool, nie „ręczny” JWKS URL

`Project decision`

JWT authorizer HTTP API przyjmuje **issuer URL** zgodny z modelem OIDC. Dla Cognito przyjmujemy canonical issuer:

`https://cognito-idp.<region>.amazonaws.com/<userPoolId>`

(`Platform requirement` — format issuer dla Cognito opisany jest w dokumentacji Amazon Cognito.)

### 2. Audience = `client_id` aplikacji klienckiej User Pool

`Project decision` + `Best practice recommendation`

W tym labie testujesz wywołanie z **tokenem Cognito** (typowo **ID token** lub **access token** — w runbooku utrzymujemy **jeden** uzgodniony wariant walidacji: **ID token** z `InitiateAuth`, bo `aud` odpowiada **app client id**). W produkcji dobór typu tokena i mapowanie claims to osobna decyzja bezpieczeństwa.

### 3. Claims do Lambdy tylko jako „bezpieczny podgląd”

`Best practice recommendation`

Handler zwraca **whitelistę** pól (`sub`, `username`/`cognito:username`, `token_use`, `iss`) — **nie** zwracaj pełnego słownika claims w odpowiedzi HTTP i **nie** loguj nagłówka `Authorization`.

### 4. CORS na czas nauki jest szeroki

`Simplification for this lab`

api_base_url = "https://eqa08dp5e0.execute-api.eu-central-1.amazonaws.com"
claims_url = "https://eqa08dp5e0.execute-api.eu-central-1.amazonaws.com/claims"
cognito_app_client_id = "58s9kfav4qv23pls46ql42q5bb"
cognito_issuer_url = "https://cognito-idp.eu-central-1.amazonaws.com/eu-central-1_N2M561qtF"
cognito_user_pool_id = "eu-central-1_N2M561qtF"
public_url = "https://eqa08dp5e0.execute-api.eu-central-1.amazonaws.com/public"

W Terraform CORS ma `allow_origins = ["*"]` — to **nie** jest wzór produkcyjny. W produkcji zawęż originy, metody i nagłówki do realnych hostów SPA.

### 5. Użytkownik testowy Cognito poza Terraform

`Simplification for this lab`

Tworzenie użytkownika i hasła wykonujesz **CLI** (`admin-create-user` / `admin-set-user-password`), żeby nie mieszać sekretów użytkownika z plikami stanu Terraform.

## Architektoniczny szkic rozwiązania

```text
Klient (curl / SPA)
  │
  ├─ GET /public  ──► HTTP API ──► Lambda (bez JWT)
  │
  └─ GET /claims  ──► HTTP API ── JWT authorizer (issuer=Cognito, aud=client_id)
                         │
                         ▼
                      Lambda (payload 2.0, claims w RequestContext)
```

### Krok 3 — Cognito: utwórz użytkownika testowego (CLI, poza Terraform)

Po `terraform apply` weź z outputów `user_pool_id` oraz `app_client_id`.

`Simplification for this lab` — poniższe wartości są przykładowe; **podmień** identyfikatory i hasło.

```bash
export POOL_ID="$(terraform output -raw cognito_user_pool_id)"
export CLIENT_ID="$(terraform output -raw cognito_app_client_id)"
export USERNAME="lab004-demo"
export PASSWORD='ChangeMe!Lab004'

aws cognito-idp admin-create-user \
  --user-pool-id "$POOL_ID" \
  --username "$USERNAME" \
  --temporary-password "TempPassw0rd!" \
  --message-action SUPPRESS

aws cognito-idp admin-set-user-password \
  --user-pool-id "$POOL_ID" \
  --username "$USERNAME" \
  --password "$PASSWORD" \
  --permanent
```

`Platform requirement` — dokładne pola i polityki haseł muszą spełniać **password policy** puli utworzonej w Terraform.

### Krok 4 — pobierz ID token (uzgodniony wariant testu)

```bash
aws cognito-idp initiate-auth \
  --auth-flow USER_PASSWORD_AUTH \
  --client-id "$CLIENT_ID" \
  --auth-parameters USERNAME="$USERNAME",PASSWORD="$PASSWORD" \
  --query 'AuthenticationResult.IdToken' \
  --output text
```

Zapisz token w zmiennej środowiskowej (uważaj na historię powłoki — `Simplification for this lab`).

## Jak poznam, że działa (walidacja)

- [ ] `terraform apply` kończy się powodzeniem.
- [ ] `curl -i "$(terraform output -raw public_url)"` zwraca **200** i JSON **bez** sekcji `claims` (trasa publiczna).
- [ ] `curl -i "$(terraform output -raw claims_url)"` **bez** nagłówka `Authorization` zwraca **401** (lub inny kod odmowy zgodny z konfiguracją JWT authorizera — ważne: brak invoke biznesowej Lambdy przy poprawnej konfiguracji authorizera dla chronionej trasy).
- [ ] `curl -i -H "Authorization: Bearer $ID_TOKEN" "$(terraform output -raw claims_url)"` zwraca **200** i JSON z polami podglądu claims zgodnymi z kodem referencyjnym.
- [ ] W odpowiedzi **nie** ma pełnego tokena ani pełnego zestawu claims (tylko whitelistę).
- [ ] W CloudWatch **nie** ma nagłówka `Authorization` / pełnego tokena w logach.

## Pułapki

1. **Pomyłka audience** — audience w authorizerze musi odpowiadać claimom w tokenie; przy Cognito najczęściej testujesz **ID token** vs **access token** świadomie, nie „na ślepo”.
2. **Nagłówek `Authorization` a identity source** — domyślnie `$request.header.Authorization`; token musi być w formacie `Bearer <jwt>`.
3. **CORS ≠ auth** — CORS nie zastępuje JWT; to osobna warstwa dla przeglądarki.
4. **Claims z koloną w nazwie** — niektóre integracje/mapowania mają ograniczenia co do nazw claims z `:`; w .NET czytaj je jako stringi ze słownika claims.
5. **User pool wymusza silne hasło** — słabe hasło = błąd CLI przy `admin-set-user-password`.
