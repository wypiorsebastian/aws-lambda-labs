# LAB-002 — Jedna funkcja Lambda, wiele tras HTTP API dla katalogu feature flags

## Goal

Zbudować jedno publiczne HTTP API o kilku trasach, które kieruje cały ruch do jednej funkcji AWS Lambda w .NET 8. Celem labu jest zrozumienie, jak API Gateway wybiera route, jak działa `ANY`, kiedy uruchamia się `$default`, oraz jak odczytać z eventu query string, parametry ścieżki i body.

## Why This Approach

W tym labie świadomie zostajemy przy **jednej funkcji Lambda** i **HTTP API**, zamiast rozdzielać endpointy na wiele funkcji lub przechodzić do REST API. To upraszcza model wdrożenia i pozwala skupić się na kontrakcie requestu, priorytecie route'ów oraz organizacji kodu handlera. W kolejnych labach można tę bazę rozszerzyć o trwałe dane, autoryzację i observability.

## Story / background

Zespół produktowy chce szybko wystawić małe API do katalogu feature flags dla aplikacji webowej. Na tym etapie nie potrzebują jeszcze prawdziwej bazy danych ani pełnego CRUD z trwałą persystencją. Potrzebują natomiast jednego publicznego endpointu HTTP, na którym da się przetestować:

- listowanie flag,
- odczyt konkretnej flagi po kluczu,
- wysłanie JSON-a do utworzenia lub aktualizacji flagi,
- zachowanie fallbacku dla nieobsługiwanych tras.

To ćwiczenie koncentruje się na warstwie transportowej i organizacji handlera. Trwałe przechowywanie danych będzie osobnym tematem.

---

## Co dokładnie ćwiczymy

- rozróżnianie tras `GET /flags`, `POST /flags`, `ANY /flags/{flagKey}` i `$default`,
- odczyt `routeKey` oraz innych pól z eventu HTTP API payload `2.0`,
- parsowanie:
  - query string dla listowania,
  - path parameter dla identyfikacji konkretnej flagi,
  - request body JSON dla operacji zapisu,
- organizację jednego handlera Lambda na kilka metod pomocniczych,
- spięcie jednej Lambdy z wieloma route'ami w Terraform.

## Czego się nauczysz

- Jak API Gateway HTTP API wybiera najbardziej dopasowaną trasę.
- Jaką rolę pełni `ANY` przy jednej funkcji Lambda obsługującej kilka metod HTTP.
- Jak działa route `$default` jako kontrolowany fallback dla nieobsługiwanych ścieżek.
- Jak w .NET 8 odczytać dane z `APIGatewayHttpApiV2ProxyRequest`.
- Jak przygotować Terraform, który mapuje kilka route'ów do jednej integracji Lambda proxy.

## Architektoniczne decyzje

### 1. Używamy `HTTP API`, nie REST API

`Project decision`

Dla lekkiego API transportowego HTTP API jest prostszym wariantem. W tym labie nie potrzebujemy jeszcze funkcji, które uzasadniałyby przejście do REST API.

### 2. Jedna Lambda obsługuje wszystkie trasy

`Project decision`

Zamiast tworzyć kilka funkcji, używamy jednego handlera i rozgałęziamy logikę po `routeKey` oraz metodzie HTTP. To pozwala skupić się na organizacji kodu i mechanice routingu.

### 3. Integracja używa `payload_format_version = "2.0"`

`Platform requirement` i `Project decision`

Poza konsolą AWS integracja HTTP API z Lambdą wymaga jawnego ustawienia `payloadFormatVersion`. W tym labie wybieramy wyłącznie `2.0`, bo ten wariant dobrze pasuje do HTTP API i upraszcza event.

### 4. Używamy jednocześnie jawnych tras i fallbacku `$default`

`Project decision`

Ćwiczymy konkretny zestaw route'ów:

- `GET /flags`
- `POST /flags`
- `ANY /flags/{flagKey}`
- `$default`

To pozwala zobaczyć różnicę między trasą statyczną, trasą z parametrem, `ANY` oraz catch-all route.

### 5. Nie wprowadzamy trwałej persystencji

`Simplification for this lab`

Ten lab nie używa DynamoDB ani innego magazynu danych. Odpowiedzi API mają pokazywać poprawny routing i parsowanie danych wejściowych, a nie produkcyjny model przechowywania flag.

### 6. Log group tworzymy w Terraform

`Best practice recommendation`

Jeżeli CloudWatch log group powstanie wcześniej automatycznie przy pierwszym invoke, Terraform może później wejść w konflikt ownership. Dlatego tworzymy ją jawnie w IaC.

## Architektoniczny szkic rozwiązania

```text
Klient HTTP
    │
    ▼
[API Gateway HTTP API]
    │  GET /flags
    │  POST /flags
    │  ANY /flags/{flagKey}
    │  $default
    ▼
[Jedna integracja Lambda proxy]
    │  payload format 2.0
    ▼
[FeatureFlagsFunction w .NET 8]
    │  dispatch po requestContext.routeKey
    │  query/path/body parsing
    ▼
[CloudWatch Logs]
```

### Jak routing ma działać

- `GET /flags`:
  - zwraca listę przykładowych flag,
  - opcjonalnie filtruje wynik po query string, np. `?enabled=true`.
- `POST /flags`:
  - przyjmuje JSON body dla nowej flagi,
  - waliduje dane wejściowe,
  - zwraca odpowiedź potwierdzającą parsowanie payloadu.
- `ANY /flags/{flagKey}`:
  - przyjmuje path parameter `flagKey`,
  - dla `GET` zwraca szczegóły jednej flagi,
  - dla `PUT` lub `DELETE` pozwala przećwiczyć dodatkowe ścieżki kodu bez tworzenia osobnych tras.
- `$default`:
  - łapie nieznane ścieżki,
  - zwraca kontrolowane `404`, zamiast pozostawiać zachowanie przypadkowi.

## Krok 4 — zbuduj dispatcher w `Function.cs`

Plik: `src/LAB-002/FeatureFlagsFunction/Function.cs`

Poniżej jest **szkielet**, nie kompletne rozwiązanie. Uzupełnij metody pomocnicze tak, aby każda trasa zwracała spójny JSON i sensowny status HTTP.

```csharp
using System.Text.Json;
using Amazon.Lambda.APIGatewayEvents;
using Amazon.Lambda.Core;

[assembly: LambdaSerializer(typeof(Amazon.Lambda.Serialization.SystemTextJson.DefaultLambdaJsonSerializer))]

namespace FeatureFlagsFunction;

public class Function
{
    public APIGatewayHttpApiV2ProxyResponse FunctionHandler(
        APIGatewayHttpApiV2ProxyRequest request,
        ILambdaContext context)
    {
        var routeKey = request?.RequestContext?.RouteKey ?? "$default";
        var method = request?.RequestContext?.Http?.Method ?? "UNKNOWN";
        var path = request?.RawPath ?? "/";

        context.Logger.LogInformation($"RouteKey={routeKey}; Method={method}; Path={path}");

        return routeKey switch
        {
            "GET /flags" => HandleGetFlags(request),
            "POST /flags" => HandlePostFlags(request),
            "ANY /flags/{flagKey}" => HandleFlagByKey(request),
            "$default" => HandleDefault(request),
            _ => HandleDefault(request)
        };
    }

    private APIGatewayHttpApiV2ProxyResponse HandleGetFlags(APIGatewayHttpApiV2ProxyRequest request)
    {
        // TODO: odczytaj query string, np. enabled=true
        // TODO: zwróć listę przykładowych flag jako JSON
        throw new NotImplementedException();
    }

    private APIGatewayHttpApiV2ProxyResponse HandlePostFlags(APIGatewayHttpApiV2ProxyRequest request)
    {
        // TODO: sparsuj request.Body do DTO i zwróć 201 albo 400
        throw new NotImplementedException();
    }

    private APIGatewayHttpApiV2ProxyResponse HandleFlagByKey(APIGatewayHttpApiV2ProxyRequest request)
    {
        // TODO: odczytaj pathParameters["flagKey"]
        // TODO: rozróżnij GET / PUT / DELETE po requestContext.http.method
        throw new NotImplementedException();
    }

    private APIGatewayHttpApiV2ProxyResponse HandleDefault(APIGatewayHttpApiV2ProxyRequest request)
    {
        var payload = new
        {
            message = "Route not found",
            routeKey = request?.RequestContext?.RouteKey,
            rawPath = request?.RawPath
        };

        return JsonResponse(404, payload);
    }

    private static APIGatewayHttpApiV2ProxyResponse JsonResponse(int statusCode, object payload)
    {
        return new APIGatewayHttpApiV2ProxyResponse
        {
            StatusCode = statusCode,
            Headers = new Dictionary<string, string>
            {
                ["Content-Type"] = "application/json"
            },
            Body = JsonSerializer.Serialize(payload)
        };
    }
}
```

## Common failure modes

### 1. Pomylenie stage `$default` z route `$default`

To dwa różne byty.

- stage `$default` wpływa na URL wywołania API,
- route `$default` jest fallbackiem routingu wewnątrz API.

W tym labie używamy obu, ale z innych powodów.

### 2. Oczekiwanie, że `ANY /flags/{flagKey}` przechwyci `POST /flags`

Nie przechwyci, bo to inna ścieżka. `POST /flags` musi mieć własną trasę.

### 3. Brak jawnego `payload_format_version = "2.0"`

Przy tworzeniu integracji poza konsolą AWS trzeba ustawić ten parametr jawnie. Inaczej łatwo skończyć z innym kontraktem eventu niż zakładany w kodzie.

### 4. Niepoprawny handler C#

W managed runtime .NET handler klasy bibliotecznej ma format:

`AssemblyName::Namespace.ClassName::MethodName`

Dla tego labu:

`FeatureFlagsFunction::FeatureFlagsFunction.Function::FunctionHandler`

### 5. Uznanie `POST /flags` za trwały zapis

`Simplification for this lab`

Jeżeli nie dodasz trwałej bazy, odpowiedź z `POST` ma tylko potwierdzać poprawne parsowanie body i reguły routingu. Nie traktuj jej jako produkcyjnej persystencji.

### 6. Pozostawienie nieobsłużonych wyjątków parsera JSON

Jeśli `JsonSerializer.Deserialize(...)` rzuci wyjątek, bez przechwycenia możesz dostać `502` albo `500`. Zadbaj o czytelną odpowiedź `400`.
