# LAB-003 — Konfiguracja środowiska Lambda, sekrety i rola wykonawcza

## Goal

Nauczyć się rozdzielać **konfigurację niepoufną** (zmienne środowiskowe funkcji Lambda) od **tajemnic** (Secrets Manager), rozumieć podstawy **roli wykonawczej** oraz świadomie wybrać miejsce przechowywania wartości wrażliwych. W tym samym labie budujesz minimalne **HTTP API** z jednym endpointem `GET /config`, który zwraca bezpieczny podgląd konfiguracji (bez wycieku pełnego sekretu w odpowiedzi HTTP).

## Why This Approach

W jednym labie mieszanie **wszystkich** opcji (SSM Parameter Store, KMS CMK, rotacja sekretów, wiele kont AWS) rozmywa przekaz. Tutaj wybieramy **jeden spójny wariant**: Lambda w .NET 8, **Secrets Manager** jako magazyn sekretu, **zmienne środowiskowe** na wartości jawne i referencje (ARN), **IAM** z minimalnym `GetSecretValue` na konkretny ARN. To jest **decyzja projektowa dla tego laba**, nie jedyna możliwa architektura w AWS.

## Story / background

Zespół ma dwa „środowiska” nazewniczo (`dev` / `test`) i jedną funkcję, która musi czytać **klucz API** przechowywany poza kodem. Nie chcą wkładać sekretu do repozytorium ani do zwykłych zmiennych środowiskowych w plaintext w Terraform (jako wartość sekretu). Chcą też widzieć w odpowiedzi API, że **etykieta środowiska** i **flagi jawne** działają, a sekret jest odczytywany dopiero w runtime z uprawnieniami roli.

## Czego się nauczysz

- Jak ustawiać **environment variables** dla funkcji Lambda i jak czytać je w .NET.
- Jak powiązać **Secrets Manager** z Lambdą przez **IAM execution role** (bez ręcznego „logowania” do AWS z kodu).
- Kiedy sensowne jest trzymanie wartości w **Secrets Manager**, a kiedy wystarczą **env vars** lub **Parameter Store** (na poziomie pojęciowym).
- Jak **nie** eksponować sekretów w logach i w odpowiedziach HTTP.
- Jak w Terraform utrzymać **spójność** między ARN sekretu, polityką IAM a kodem.

## Założenia

- Ukończyłeś `LAB-002` albo rozumiesz ten sam stos: **HTTP API** + **Lambda proxy** + **payload 2.0** + `terraform apply`.
- Region: **`eu-central-1`** (**decyzja projektowa** tego laba).
- Runtime: **`dotnet8`**, architektura **`x86_64`** (**decyzja projektowa**).
- Masz lokalnie .NET SDK 8.x, Terraform ≥ 1.6, skonfigurowane poświadczenia AWS.
- Struktura kodu zgodna z konwencją repo: `src/LAB-003/<Projekt>/`, artefakt: `artifacts/LAB-003/function.zip`.

## Decyzje architektoniczne

### 1. Sekret jest w Secrets Manager, nie w env Lambda

`Project decision` + `Best practice recommendation`

Wartość wrażliwa (`demoApiKey`) żyje w **Secrets Manager**. W zmiennych środowiskowych Lambdy trzymamy wyłącznie **`SECRET_ARN`** (referencja), bo sama nazwa ARN **nie jest** sekretem — ale nadal warto nie wyświetlać jej publicznie bez potrzeby.

### 2. Nie poufne ustawienia trafiają do env

`Project decision`

`APP_ENV` oraz `PUBLIC_FEATURE_TOGGLE` to przykłady **jawnej** konfiguracji sterowanej Terraform (`-var` / `terraform.tfvars`).

### 3. „Środowisko” modelujemy etykietą `app_env`, nie osobnym kontem AWS

`Simplification for this lab`

Pełna izolacja dev/test na poziomie kont lub organizacji to osobny temat operacyjny. Tu ćwiczysz **mechanikę** zmiennych i sekretu w jednym koncie.

### 4. Szyfrowanie env w spoczynku — domyślne zachowanie AWS

`Platform requirement`

Lambda **szyfruje** zmienne środowiskowe w spoczynku — domyślnie kluczem zarządzanym przez usługę. Osobny **CMK** (KMS) bywa wymagany polityką compliance — w tym labie tylko **linkujemy** dokumentację, bez pełnego wdrożenia CMK.

### 5. Usuwanie sekretu w tym labie

`Simplification for this lab`

W **AWS Secrets Manager** usunięcie sekretu **zwykle nie następuje od razu** w sensie „znika natychmiast i koniec”. Zamiast tego AWS często **planuje** usunięcie i wprowadza **okres**, w którym można jeszcze **cofnąć** tę operację. Ten okres nazywa się **recovery window** (okno odzyskiwania). W typowym scenariuszu może on trwać **co najmniej 7 dni**, a **domyślnie bywa około 30 dni** — dokładne wartości i reguły są opisane w dokumentacji Secrets Manager (`Simplification for this lab`: tu nie musisz znać wszystkich wariantów na pamięć, ważne jest samo pojęcie).

W tym labie **upraszczamy temat**: chcemy, żeby `terraform destroy` **posprzątał zasoby możliwie szybko** i **nie blokował** dalszej nauki długim „oczekiwaniem na ostateczne usunięcie”. W szkielecie Terraform, w zasobie `aws_secretsmanager_secret`, ustawiamy `recovery_window_in_days = 0`, co przy usuwaniu zasobu oznacza **brak takiego okresu ochronnego** w rozumieniu powyżej — zgodnie z modelem opisanym w dokumentacji Terraform dla tego atrybutu.

To jest **uproszczenie wyłącznie na potrzeby ćwiczenia**.

W **środowisku produkcyjnym** dłuższy okres ochronny ma często sens, bo pozwala **odzyskać sekret usunięty przez pomyłkę**. AWS traktuje usuwanie sekretów ostrożnie właśnie dlatego, że są to dane krytyczne — decyzja o oknie odzyskiwania i procedurach to wtedy **świadomy wybór operacyjny**, nie „domyślne skróty z laba”.

## Architektoniczny szkic rozwiązania

```text
Klient
  │
  ▼
HTTP API  GET /config   (payload 2.0)
  │
  ▼
Lambda (.NET 8)
  │  odczyt APP_ENV, PUBLIC_FEATURE_TOGGLE (env)
  │  odczyt sekretu: Secrets Manager API (SDK)
  │  IAM: secretsmanager:GetSecretValue na dany ARN
  ▼
Secrets Manager  (JSON: demoApiKey)
```

## Krok po kroku

### Krok 1 — utwórz projekt funkcji

Z katalogu głównego repo:

```bash
mkdir -p src/LAB-003
cd src/LAB-003
dotnet new lambda.EmptyFunction --name ConfigLabFunction
cd ConfigLabFunction
```

Handler docelowy (class library) ma postać:

`ConfigLabFunction::ConfigLabFunction.Function::FunctionHandler`

### Krok 2 — dodaj zależności

```bash
dotnet add package Amazon.Lambda.APIGatewayEvents
dotnet add package AWSSDK.SecretsManager
```

### Krok 3 — handler (implementacja w repo)

Plik: `src/LAB-003/ConfigLabFunction/Function.cs`

W repozytorium jest **gotowa referencyjna implementacja**, żebyś mógł porównać kod z Terraformem i walidacją. Zrób `dotnet build` i przejrzyj handler przed pakowaniem ZIP.

Handler robi następujące rzeczy (zgodnie z celem laba):

- odczytuje `APP_ENV`, `PUBLIC_FEATURE_TOGGLE`, `SECRET_ARN` ze `Environment.GetEnvironmentVariable`;
- wywołuje `GetSecretValue` na `SECRET_ARN` przez `AmazonSecretsManagerClient`;
- wyciąga z JSON pola sekretu pole `demoApiKey` (patrz `aws_secretsmanager_secret_version` w Terraformie);
- w odpowiedzi HTTP zwraca m.in. `demoApiKeyLast4` (**ostatnie 4 znaki**), nigdy pełnej wartości;
- w logach zapisuje tylko etykiety środowiska i fakt obecności `SECRET_ARN`, **bez** treści sekretu;
- przy błędzie odczytu sekretu zwraca odpowiedź JSON z kodem błędu i ogólnym komunikatem (szczegół typu wyjątku tylko w CloudWatch — nadal bez wartości sekretu).

Jeśli uczysz się „od zera”, możesz skopiować plik do notatek i **przepisać** go samodzielnie krok po kroku zamiast wklejać — wtedy ćwiczysz ten sam przepływ ręcznie.

### Krok 4 — spakuj ZIP

```bash
mkdir -p ../../../artifacts/LAB-003
dotnet lambda package --output-package ../../../artifacts/LAB-003/function.zip
```

### Krok 5 — Terraform / IaC

Szkielet jest w `infra/terraform/labs/LAB-003/`:

- `main.tf` — Lambda, HTTP API, Secrets Manager, IAM.
- `variables.tf` — m.in. `app_env`.
- `outputs.tf` — URL-e do walidacji.
- `README.md` — skrót operacji.

Przed `apply` upewnij się, że:

- `handler` w Terraform = `ConfigLabFunction::ConfigLabFunction.Function::FunctionHandler` (dopasuj do swojej przestrzeni nazw, jeśli zmienisz kod).
- istnieje plik `artifacts/LAB-003/function.zip`.

Przykład zmiany etykiety środowiska (**wersjonowanie konfiguracji przez zmienne Terraform**):

```bash
cd infra/terraform/labs/LAB-003
terraform init
terraform apply -var="app_env=test"
```

### Krok 6 — wdrożenie

```bash
cd infra/terraform/labs/LAB-003
terraform plan
terraform apply
```

## Jak poznam, że działa (walidacja)

- [ ] `terraform apply` kończy się powodzeniem.
- [ ] `terraform output -raw config_url` zwraca URL kończący się na `/config`.
- [ ] `curl -i "$(terraform output -raw config_url)"` zwraca **200** i JSON z polami pokazującymi `app_env` oraz flagę jawną (np. `publicFeatureToggle`).
- [ ] W odpowiedzi **nie** ma pełnej wartości sekretu — wyłącznie bezpieczny podgląd (np. `demoApiKeyLast4`) lub równoważnik uzgodniony w kodzie.
- [ ] W CloudWatch Logs **nie** ma pełnego sekretu w logach.
- [ ] Po zmianie `-var="app_env=..."` i ponownym `apply` widzisz nową wartość `APP_ENV` w odpowiedzi (świadoma zmiana „wersji konfiguracji” przez redeploy).

## Pułapki

1. **Sekret w plaintext w Terraform** — `aws_secretsmanager_secret_version` w tym labie zawiera przykładowy JSON dla nauki. W realnym repo często używa się referencji z zewnętrznego źródła lub ręcznego wprowadzenia poza TF; nie kopiuj wzorca bezrefleksyjnie do produkcji.

2. **Za szerokie IAM** — nadaj `secretsmanager:GetSecretValue` tylko na **konkretny ARN** sekretu (tak jest w szkielecie), nie na `*`.

3. **Zmiana sekretu a cache** — Lambda może **ponownie użyć** tego samego środowiska; jeśli testujesz zmianę wartości sekretu, pamiętaj o ewentualnym „świeżym” invoke (lub osobnej funkcji testowej). To jest **niuans operacyjny**, nie błąd Terraform.

4. **Mylenie „encryption at rest env” z „sekret w env”** — szyfrowanie env przez AWS **nie zastępuje** braku sekretów w plaintext w konsoli/TF dla wartości wrażliwych.

5. **Ścieżka ZIP** — musi zgadzać się z `lambda_zip_path` w module (względem `infra/terraform/labs/LAB-003`).

## Cleanup i cost hygiene

```bash
cd infra/terraform/labs/LAB-003
terraform destroy
```

Po destroy sprawdź w konsoli lub przez CLI, że zniknęły: funkcja, API, rola (poza managed policy attachment), sekret (w tym szkielecie — patrz sekcja *„Usuwanie sekretu w tym labie”* powyżej: `recovery_window_in_days = 0`). Usuń lokalnie `artifacts/LAB-003/function.zip`, jeśli nie chcesz go trzymać.

Nie zostawiaj publicznego API bez potrzeby — koszt i powierzchnia ataku.
